## 实测结果

以下结果来自两台机器上、输入不同的几次独立测试。共同设置为 BF16、PyTorch SDPA、8 步、
1280×704、24 fps。DiT 常驻显存，VAE 使用运行时自动选择的 layerwise offload；未启用
SageAttention、Cache-DiT、`torch.compile` 和合并 QKV。服务已完成内置预热；"首条请求"指启动后的
第一条正式请求，不含模型加载时间。

### 单卡

单张 NVIDIA H20，SP1，seed 42。输入为 OpenS2V-Eval 中的一个三参考图 case（人物、狗、建筑），
提示词经过改写，参考图直接使用该 case 的原始照片。这是功能验收，不是 OpenS2V-Eval 的官方榜单结果；
单个 case 也不代表系统性的画质评测。

| 请求 | 帧数 | API 推理耗时 | 客户端等待完成 | 峰值 reserved 显存 |
| --- | ---: | ---: | ---: | ---: |
| 三参考图生成，首条请求 | 121 | 100.60 s | 103.42 s | 80,472 MiB |
| 三参考图生成，重复请求 | 121 | 98.80 s | 100.86 s | 80,436 MiB |
| 续写：17 帧前缀 + 120 帧新内容 | 137 | 45.23 s | 48.25 s | 76,422 MiB |

各阶段耗时：

| 阶段 | 三参考图生成（首条） | 续写 |
| --- | ---: | ---: |
| 文本编码 | 0.234 s | 0.239 s |
| 参考图 / 前缀 VAE 编码 | 0.975 s | 0.756 s |
| DiT 八步 | 95.652 s | 40.048 s |
| 音视频解码 | 3.674 s | 4.112 s |

续写使用的是已生成视频的末尾，并且没有参考图，所以 token 数与生成请求不同：137 帧的片段共
15,840 个 token，其中 17 帧前缀（3 个 latent 帧）占 2,640 个。两行之间的耗时差异不能当作同一任务的提速，
见[参考图尺寸](#参考图尺寸)。

### 4 卡

4 张 141 GB（HBM3e）版 NVIDIA H20，使用 `configs/4gpu-ulysses.json`（Ulysses SP4），seed 42。
这次测试与上面的单卡测试机器不同、case 也不同：在一个合成 case 上运行验收脚本（`scripts/acceptance.py`），
三张参考图都较小（768×768、768×768 和 1280×704 像素）。"单张 H20"一列是同一 case 在同一台机器的一张卡上的结果。

| 请求 | 帧数 | 单张 H20 | 4 张 H20 | 每卡峰值 reserved 显存（4 张 H20） |
| --- | ---: | ---: | ---: | ---: |
| 生成，首条请求 | 121 | 44.8 s | 16.1 s | 78,852 MiB |
| 生成，重复请求 | 121 | 43.7 s | 15.4 s | 79,766 MiB |
| 续写，17 + 120 帧 | 137 | 44.8 s | 18.8 s | 80,866 MiB |

耗时为 API 推理耗时。多卡输出与单卡不是逐位一致（并行计算的顺序不同，与单卡结果的 PSNR 为 34–37 dB），画面内容相同。

### 参考图尺寸

参考图不会缩放到输出分辨率。每张参考图按接近原图的尺寸编码（保持宽高比，取整到 32 像素的倍数），
向每一步 DiT 都要处理的序列追加 (宽 / 32) × (高 / 32) 个 token；1280×704 的 121 帧片段本身有
14,080 个 token。768×768 的图追加 576 个 token，1280×704 的图 880 个，2048×2048 的图 4,096 个，
4000×3000 的照片 11,750 个。

在 4 张 141 GB 的 H20 上实测，5 秒片段，种子 7（测了多次的另用种子 1–3）。参考图来自一个 Agent
世界：在纯色影棚背景上画的 1328×1328 角色图和一张 1664×928 的地点图，再缩放到各个尺寸。
A：两个角色加地点；B：三个角色加地点。

| 参考图 | A：参考图 token | A：推理时间 | B：参考图 token | B：推理时间 |
| --- | ---: | ---: | ---: | ---: |
| 缩放到 512×512 | 764 | 14.8 秒 | 1,020 | 14.8 秒（4 次） |
| 缩放到 768×768 | 1,728 | 15.4 秒（4 次） | 2,304 | 16.9 秒 |
| 缩放到 1024×1024 | 3,080 | 16.9 秒 | 4,104 | 17.9 秒 |
| 原尺寸，裁掉背景 | 3,230 | 17.0 秒（3 次） | 3,986 | 17.8 秒（4 次） |
| 原尺寸（每张约 180 万像素） | 5,036 | 18.5 秒（4 次） | 6,800 | 20.1 秒（4 次） |
| 缩放到 2048×2048 | 12,320 | 26.5 秒（3 次） | 16,416 | 31.4 秒 |
| 其中一个角色换成 1200 万像素照片 | 15,153 | 29.9 秒 | | |
| 三张都是 1200 万像素照片 | 35,507 | 58.5 秒 | | |

同一请求重复运行，耗时相差不到 0.5 秒。参考图编码只占 0.1–1.4 秒，其余差别都在 DiT 各步里，
并且比 token 数增长得更快。40 次运行的峰值预留显存都在 84,098–88,742 MiB 之间，5 秒片段下
参考图大小对显存没有明显影响。

从画面看，比原图更大的参考图（2048×2048、1200 万像素）并没有让角色更像；缩到 768×768 时，
女主角的脸不如原图像。裁掉画出来的角色周围的纯色背景后，画面与原图相当。三个角色同框时，
每种尺寸下都有约一半的片段丢掉一个角色或把两个人合成一个，这种情况与尺寸无关，本身就不稳定。
每种尺寸只测了几个种子，不能代替画质评测。

参考图请保持在出图模型画出的尺寸左右（约 180 万像素），并裁掉纯色背景；
[Murea Agent](../../agent/README_zh.md#片段时长) 在发送前会做这两件事。

参考图大小很可能就是两次单卡测试结果不同的原因。不带参考图的续写在两次测试中都约 45 秒。合成参考图追加
2,032 个 token，所以那次生成（16,112 个 token）与 15,840 个 token 的续写耗时相当。在 OpenS2V
那次测试中，生成的 DiT 除第一步外每步约 11.8 秒，而同一台机器上的续写每步 4.8 秒，说明那三张照片
追加的 token 要多得多。那次测试没有记录照片的像素尺寸，也没有分别改变机器和参考图做对比，
因此原因并未通过测量单独确认。

### 片段时长

时长由 `num_frames` 决定：任意 `8n+1` 帧，最多 481 帧（20 秒），即模型的位置编码范围。续写时前缀也计入其中。
4 张 141 GB 版 H20、两张真实照片参考图、同一提示词、seed 7：

| 片段 | 帧数 | API 推理耗时 | 客户端等待 | 每卡峰值 reserved 显存 |
| --- | ---: | ---: | ---: | ---: |
| 5 秒 | 121 | 17.0 s | 19.6 s | 81,486 MiB |
| 10 秒 | 241 | 34.7 s | 38.9 s | 92,260 MiB |
| 15 秒 | 361 | 56.1 s | 62.2 s | 103,396 MiB |
| 20 秒 | 481 | 80.8 s | 88.6 s | 114,206 MiB |
| 续写，17 帧前缀 + 10 秒 | 257 | 37.0 s | 42.0 s | 93,238 MiB |

所有输出都完整解码，音轨与视频等长。在每段中均匀抽帧检查，20 秒以内两个人物和场景都保持一致，续写能从上一段的最后一帧接下去。单个提示词不代表系统性的画质评测。推理耗时随时长增长，略快于线性：在 4 卡上，5 秒片段每秒视频约需 3.4 秒推理时间，20 秒片段约需 4.0 秒。

峰值 reserved 显存只统计 PyTorch 的分配，CUDA context 和通信缓冲区另计。只有 5 秒片段的每卡显存低于 96 GB（96 × 10⁹ 字节，约 91,553 MiB）。从 10 秒起（包括续写），每卡 reserved 显存都超过这一数值（10 秒为 92,260 MiB，约 96.7 GB），因此尚未证明这些时长能在 96 GB 版 H20 上运行。

单张 H20 只测过 5 秒片段，reserved 显存最高 80,472 MiB（约 79 GiB），更长的片段请使用多卡。

软件版本：Torch 2.13.0、Transformers 5.12.1、Diffusers 0.37.0、Triton 3.7.1、
sglang-kernel 0.4.6.post1（完整列表见[部署说明](deployment_zh.md#环境)）。

**尚未用此权重验证**：单卡生成 5 秒以上的片段、在显存小于 141 GB 的 GPU 上生成 10 秒及更长的片段、
2 卡或 8 卡配置、TP、SageAttention、合并 QKV、`torch.compile`、H20 以外的 GPU、长时间并发负载、
续写接缝处的音频连续性，以及多 case 画质。仓库保留了这些配置，但不宣称它们在画质或速度上的收益。

## 优化开关

基线为 BF16、SDPA、8 步、one-stage。任何改动都应与基线在相同的权重、输入、seed、
分辨率、时长、并行方式和软件版本下对比。

| 机制 | 状态 | 配置与限制 |
| --- | --- | --- |
| 常驻服务 | 已包含 | 一次加载可处理多个请求；各阶段的卸载由底层组件管理决定 |
| Ulysses 序列并行 | 已包含 | `parallel: ulysses`，1/2/4/8 卡；切分的是序列，不是按层切模型 |
| 张量并行 | 上游路径 | `parallel: tp`；非默认，需要单独测量 |
| 合并 QKV 的 all-to-all | 可选 | `packed_qkv: true`；把 Q/K/V 三次通信合并为一次。只改变数据搬运方式，不满足条件的输入会回退到不合并的路径。不是低精度通信 |
| SageAttention | 可选，近似计算 | `attention: sage_attn` 并设置 `sage_pythonpath`；结果与 SDPA 不逐像素一致 |
| `torch.compile` | 可选，实验性 | `compile: true`；首次编译时间不计入热推理耗时，需要单独验证 |
| Cache-DiT / 跳步 | 关闭 | 只有 8 步，不再进一步跳步 |
| 跨请求 KV cache | 未使用 | 双向注意力且 timestep 不断变化，无法复用 |
| clean-latent 续写 | 已实现 | 前缀固定，只对新增部分去噪；音频重新生成；不是分块流式生成 |

## 如何测量

每个请求都会记录输入、`timing.json`、可选的 `perf_dump_path` 输出和 FFprobe 报告。
运行目录中的 `service.json` 记录启动命令和所有运行源码文件的 SHA-256，
可以把结果追溯到实际运行的代码。

服务端的 `inference_time_s` 和客户端等待时间分开记录。`peak_memory_mb` 是 PyTorch reserved
显存峰值除以 1024²，单位是 MiB；多卡时不是各卡之和。

做性能测试时，先让服务预热，再用同一个 case 和 seed 跑多轮。`scripts/acceptance.py`
会把生成跑两次、续写跑一次，并校验每个输出，见[部署说明](deployment_zh.md#端到端检查)。
